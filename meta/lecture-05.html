1. Зачем нужен препроцессор

Что происходит с исходным кодом до компиляции:

Когда мы пишем программу на C++, может показаться, что компилятор сразу берёт исходный .cpp-файл и компилирует его.

На самом деле перед компиляцией исходный файл проходит дополнительный этап — предварительную обработку.

Предварительную обработку выполняет программа препроцессор, которая вносит различные изменения в текст файла кода. Препроцессор фактически никак не изменяет исходные файлы кода — все изменения, вносимые препроцессором, происходят либо временно в памяти, либо с использованием временных файлов.

Когда препроцессор завершает обработку файла кода, результат называется единицей трансляции . Именно эта единица трансляции затем компилируется компилятором.

Упрощённо процесс можно представить так:

Исходный код
        ⬇
    Предварительная обработка
            ↓
            └➔ Результат предварительной обработки
                    ⬇
                Компиляция
                  ↓
                  └➔ Объектный файл
                           ⬇
                        Компоновка
                        ↓
                        └➔ Исполняемая программа

На этапе предварительной обработки препроцессор работает прежде всего с текстом программы. Он обрабатывает специальные конструкции, называемые директивами препроцессора.

В современных компиляторах препроцессор обычно интегрирован в общий процесс обработки программы, поэтому программисту не требуется запускать его как отдельную программу.

В совокупности предварительную обработку, компиляцию и компоновку можно рассматривать как части процесса трансляции программы.

2. Директивы препроцессора

Директивы препроцессора начинаются с символа #.

Например:

#include <iostream>

или:

#define SIZE 10

Директива препроцессора не является обычной инструкцией языка Си / C++. Поэтому после неё не ставится точка с запятой:

#define SIZE 10

Препроцессор обрабатывает исходный файл последовательно, начиная с его начала.

При этом он не анализирует программу так, как это делает компилятор C++. Препроцессор работает с директивами, имеющими собственный синтаксис.

Наиболее важные директивы:

#include
#define
#ifdef
#ifndef
#endif

Директива #include

#include <iostream>

Упрощённо можно считать, что директива #include приводит к включению содержимого указанного файла в текущую единицу трансляции.

Например:

#include <iostream>

int main() {
    std::cout << "Hello\n";
}

после предварительной обработки объявления и другие необходимые элементы, предоставляемые заголовком <iostream>, становятся частью текущей единицы трансляции.

Конечно, реальная реализация стандартных заголовков значительно сложнее, поэтому воспринимать это следует именно как упрощённую модель работы #include.

Особенно важно, что включённый файл сам может содержать директивы #include.

Например:

// A.h
#include "B.h"

Если написать:

#include "A.h"

то при обработке A.h препроцессор встретит ещё один #include и обработает B.h.

Получается цепочка:

main.cpp
   │
   └── A.h
        │
        └── B.h

Именно механизм включения файлов станет особенно важен, когда мы перейдём к заголовочным файлам.

Макросы и #define

Другой важной директивой является:

#define

Макросы, определяемые с помощью #define, можно разделить на несколько видов. Существует два основных типа макросов: объектно-подобные макросы и функционально-подобные макросы.

Идентификатор макроса использует те же правила именования, что и обычные идентификаторы: он может содержать буквы, цифры и символы подчеркивания, не может начинаться с цифры и не должен начинаться с символа подчеркивания.

Объектоподобные макросы

Макрос можно рассматривать как правило, по которому препроцессор преобразует текст программы.

#include <iostream>

#define MY_NAME "Alex"

int main() {
    std::cout << "My name is: " << MY_NAME << '\n';

    return 0;
}

После предварительной обработки соответствующий фрагмент будет выглядеть примерно так:

std::cout << "My name is: " << "Alex" << '\n';

В результате программа выведет:

My name is: Alex

или

#define SIZE 10

Здесь SIZE заменяется текстом 10.

По соглашению имена макросов часто записывают заглавными буквами:

#define MAX_SIZE 100
#define BUFFER_SIZE 256

Это позволяет визуально отличать макросы от обычных идентификаторов C++.

Макросы с подстановочным текстом сейчас встречаются в основном в устаревшем коде, рекомендуется избегать их использования, когда это возможно.

Почему макросы с текстовой подстановкой следует использовать осторожно

  • Отсутствие контроля типов: Препроцессор не проверяет типы данных аргументов. Это это может привести к неожиданным ошибкам и странному поведению программ.
  • Проблемы с приоритетом операций: При подстановке выражений без скобок легко получить баги. Например, макрос
    #define SQUARE(x) x * x при вызове SQUARE(1 + 2) превратится в 1 + 2 * 1 + 2, что равно 5 вместо 9.
  • Повторное вычисление аргументов: Если передать в макрос выражение с побочным эффектом (например, SQUARE(x++)), код увеличит переменную x дважды.
  • Сложная отладка: Ошибки компиляции в макросах выдают непонятные сообщения, так как компилятор видит уже развернутый препроцессором текст, а не то, что написал программист.
  • Отсутствие областей видимости (namespace): Макросы не подчиняются областям видимости C++. После определения макрос действует далее в обрабатываемом исходном тексте до #undef или до конца соответствующей единицы трансляции.
  • Трудности при пошаговой отладке: Макрос не является функцией, поэтому его отладка существенно отличается от пошаговой отладки обычной функции. Отладчик работает с кодом после предварительной обработки.

Поэтому макросы с текстовой подстановкой сегодня применяются значительно осторожнее, чем в старом коде на C и C++.

Макросы без текста подстановки

Макрос можно определить и без текста после имени:

например:

#define DEBUG

В этом случае макрос не предназначен для замены одного текста другим.

Сам факт того, что макрос определён, можно использовать для условной компиляции.

Например:

#include <iostream>

#define PRINT_JOE

int main()
{
#ifdef PRINT_JOE
    std::cout << "Joe\n";
#endif

#ifdef PRINT_BOB
    std::cout << "Bob\n";
#endif

    return 0;
}

Если PRINT_JOE определён, этот участок программы будет включён в результат предварительной обработки.

Если PRINT_JOE не определён, этот участок будет исключён.

Условная компиляция

Основные директивы:

#ifdef
#ifndef
#if
#elif
#else
#endif

В отличие от обычных макросов-функций, они управляют тем, какой именно кусок кода вообще попадет в компилятор, а какой будет полностью проигнорирован.Они обрабатываются на этапе препроцессора (до компиляции) и незаменимы для настройки кроссплатформенности и защиты от повторного включения файлов.

#ifdef (IF DEFined)

— проверяет, существует ли (определен ли) указанный макрос. Если макрос определён, соответствующий блок исходного текста включается в результат предварительной обработки и затем может быть передан компилятору.

#ifndef (IF NOT DEFined)

— противоположность ifdef. Код компилируется, только если макрос НЕ определен.

#elif (ELSE IF)

— позволяет задать альтернативное условие, если предыдущие проверки вернули ложь.

#endif (END IF)

— обязательная директива, которая закрывает блок условной компиляции.

Главные сценарии использования

  1. Include Guards (Защита заголовков от повторного включения).

Самый частый сценарий в C++. Защищает от ошибок «повторное определение», если один и тот же .h-файл был случайно подключен несколько раз.

#ifndef MY_HEADER_H
#define MY_HEADER_H

// Весь код файла пишется здесь.
// Содержимое заголовка будет включено в эту единицу трансляции только один раз.

    // ...


#endif // MY_HEADER_H

В современном C++ вместо этого чаще пишут одну строчку #pragma once.

Hо include guard на основе #ifdef, #define и #endif использует стандартные возможности препроцессора C++, а#pragma once — удобный, но нестандартный способ защитить заголовочный файл от повторного включения. Его главное преимущество — простота. Главный недостаток — отсутствие гарантии стандартом C++.

  1. Кроссплатформенность

Позволяет компилировать разный код в зависимости от операционной системы или архитектуры процессора.

#ifdef _WIN32
    // Код, который работает только на Windows
    #include <windows.h>
#elif defined(__linux__)
    // Код, который работает только на Linux
    #include <unistd.h>
#elif defined(__APPLE__)
    // Код для macOS
#endif
  1. Отладочный код (Debug / Release)

Помогает оставлять «тяжелые» логи или проверки только в процессе разработки, полностью вырезая их из финальной (Release) версии программы для оптимизации скорости.

#ifdef DEBUG_MODE
    std::cout << "Лог: переменная x = " << x << std::endl;
#endif

Разница между условной компиляцией и обычным if

Критерий Директивы (#ifdef) Обычный if в C++
Когда работает На этапе препроцессора (до компиляции) Во время работы программы (Runtime)
Что происходит с кодом Неактивная ветка не включается в результат предварительной обработки и не передаётся компилятору. Обе ветки являются частью исходного C+±кода и должны быть корректными для компиляции; компилятор и оптимизатор затем решают, какой код оставить в итоговой программе.
Проверка синтаксиса В неактивной ветке может быть даже некорректный код — компилятор не выдаст ошибку. Код в обеих ветках должен быть синтаксически правильным.

Функционально-подобные макросы (function-like macros)

В отличие от объектноподобных макросов, которые просто заменяют одно имя на кусок кода, функционально-подобные макросы позволяют динамически подставлять переданные в них значения в тело макроса перед компиляцией.

Синтаксис объявления

#define ИМЯ_МАКРОСА(аргумент1, аргумент2, ...) тело_макроса

Важное правило: между именем макроса и открывающей скобкой ( не должно быть пробелов. Если поставить пробел, препроцессор посчитает макрос объектно-подобным, а скобки — частью заменяемого текста.

#include <iostream.h>

#define MAX(a, b) (a > b) ? a : b

int main() {
    int x {10};
    int y {20};

    int result {MAX(x, y)};
    // Препроцессор заменит это на: int result { x > y ? x : y };

    std::cout << result << '\n';
    return 0;
}

В современном C++ вместо функционально-подобных макросов настоятельно рекомендуется использовать inline-функции или шаблоны (templates), так как они безопаснее и поддерживают строгую проверку типов.

3. Несколько файлов в C++

По мере роста программы один исходный файл становится неудобным.

Поэтому программу разбивают на несколько файлов.

Например:

main.cpp
add.cpp

В add.cpp находится определение функции:

int add(int x, int y) {
    return x + y;
}

А в main.cpp мы хотим вызвать эту функцию:

#include <iostream>

int add(int x, int y);

int main() {
    std::cout << add(3, 4) << '\n';

    return 0;
}

Перед вызовом функции находится её объявление:

int add(int x, int y);

Оно сообщает компилятору main.cpp, что функция add существует и какой у неё интерфейс.

После компиляции отдельных исходных файлов компоновщик связывает вызов функции из main.cpp с её определением в add.cpp.

Схематично:

main.cpp                         add.cpp
   │                                │
   │ объявление add()              │ определение add()
   ↓                                ↓
компиляция                       компиляция
   │                                │
   └──────────────┬─────────────────┘
                  ↓
             компоновка
                  ↓
          готовая программа

Это один из фундаментальных принципов организации многофайловых C+±проектов.

Почему компилятор не запоминает другие .cpp-файлы

Очень важно понять следующий момент.

Каждый исходный .cpp-файл обрабатывается в составе своей единицы трансляции и компилируется независимо от других .cpp-файлов.

Когда он компилирует:

main.cpp

он не обязан знать содержимое:

add.cpp

Поэтому определение:

int add(int x, int y) {
    return x + y;
}

само по себе не делает функцию известной компилятору при обработке другого файла.

Для этого в main.cpp необходимо объявление:

int add(int x, int y);

Позже компоновщик сопоставит вызов функции с её определением.

Такое разделение позволяет:

  • изменять один исходный файл без необходимости заново компилировать все остальные;
  • компилировать файлы независимо;
  • организовывать большие программы по отдельным компонентам.

4. Заголовочные файлы

Если проект содержит много функций, постоянно писать их объявления вручную в каждом .cpp становится неудобно.

Для этого используются заголовочные файлы.

Например:

add.h
add.cpp
main.cpp

В add.h помещаем объявление:

int add(int x, int y);

В add.cpp:

#include "add.h"

int add(int x, int y) {
    return x + y;
}

В main.cpp:

#include "add.h"
#include <iostream>

int main() {
    std::cout << add(3, 4) << '\n';

    return 0;
}

Теперь оба .cpp-файла получают объявление функции через:

#include "add.h"

Заголовочный файл позволяет вынести общий интерфейс в отдельное место.

Упрощённо можно представить организацию так:

              add.h
             /     \
            /       \
           ↓         ↓
      main.cpp     add.cpp
           \         /
            \       /
             ↓     ↓
             программа

Проблема повторного включения (One Definition Rule)

Использование #include приводит к важному вопросу.

Что произойдёт, если один и тот же заголовочный файл будет включён несколько раз?

Возникает повторное определение, а это ошибка.

Следовательно, заголовочные файлы должны быть защищены от многократного включения в одну единицу трансляции.

Для этого используется механизм header guard, или защита заголовочного файла, который был рассмотрен выше при изучении условной компиляции.

Итоговая схема

В результате организацию небольшого многофайлового проекта можно представить следующим образом:

                Заголовочный файл
                     add.h
                       │
              ┌────────┴────────┐
              ↓                 ↓
           main.cpp           add.cpp
              │                 │
              │                 │
          вызов add()       определение add()
              │                 │
              └────────┬────────┘
                       ↓
                   компоновка
                       ↓
                 программа

А работа препроцессора с заголовочным файлом:

main.cpp
   │
   ├── #include "add.h"
   │
   ↓
предварительная обработка
   │
   ↓
результат предварительной обработки с включённым содержимым add.h
   │
   ↓
компиляция

Именно эти механизмы позволяют разделять программу на несколько исходных файлов, организовывать интерфейсы компонентов и управлять тем, какой код участвует в компиляции.

5. extern

Теперь еще одна важная конструкция.

Представим глобальную переменную:

// config.cpp

int kGlobalValue{42};

Другой файл хочет обратиться к ней:

// main.cpp

extern int kGlobalValue;

extern объявляет переменную, определение которой находится в другой единице трансляции (или в другом месте программы), и позволяет использовать эту переменную в текущей единице трансляции.

После этого:

std::cout << kGlobalValue;

может обратиться к переменной.

Программа может состоять из нескольких единиц трансляции, и им иногда требуется ссылаться на одни и те же сущности.

Но глобальное состояние следует использовать осторожно.

6. Scope, lifetime и linkage

Теперь связываем несколько лекций.

Мы уже знаем:

Scope - где имя доступно.

Lifetime - как долго существует объект.

Linkage - (связывание) — определяет, может ли одно и то же имя обозначать одну и ту же сущность в разных единицах трансляции.**

7. Правило одного определения (One Definition Rule, ODR)

Правило одного определения (или сокращенно ODR) — это хорошо известное правило в C++. Правило ODR состоит из трех частей:

  • Внутри файла каждая функция, переменная, тип или шаблон в заданной области видимости может иметь только одно определение. Определения, встречающиеся в разных областях видимости (например, локальные переменные, определенные внутри разных функций, или функции, определенные внутри разных пространств имен), не нарушают это правило.
  • Внутри программы каждая функция или переменная в заданной области видимости может иметь только одно определение. Это правило существует потому, что программы могут иметь более одного файла. Функции и переменные, невидимые для компоновщика, исключаются из этого правила.
  • Типы, шаблоны, встроенные функции и встроенные переменные могут иметь дублирующиеся определения в разных файлах, при условии, что каждое определение идентично.
