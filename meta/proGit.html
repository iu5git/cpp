git и GitHub: как перестать бояться изменений

Представьте себе ситуацию.

Вы написали программу.

Она работает.

Вы смотрите на неё и думаете:

«Ну всё. Красота. Я наконец-то сделал это».

И тут вам приходит в голову гениальная мысль:

«А что если я сейчас немного улучшу код?»

Вы меняете одну строчку.

Программа перестаёт работать.

Вы меняете вторую.

Перестаёт работать ещё сильнее.

Вы пытаетесь вернуть всё обратно.

И через некоторое время у вас появляются файлы:

program.cpp

program_new.cpp

program_final.cpp

program_final2.cpp

program_final_really.cpp

program_final_really_2.cpp

program_old.cpp

program_old_old.cpp

А потом вы уже не знаете, какой из них последний.

git появился примерно для того, чтобы программисты больше не жили так.

Представим, что мы снимаем фильм

Давайте представим, что ваш проект — это фильм.

Вы написали первую версию.

Это кадр №1:

Проект

Потом исправили ошибку.

Получился кадр №2.

Потом добавили новую функцию.

Кадр №3.

Потом что-то сломали.

Кадр №4.

И git позволяет нам сказать:

«Я хочу сохранить историю того, как мой проект развивался».

Каждый раз, когда мы сознательно фиксируем состояние проекта, мы создаём commit.

То есть commit — это не просто «сохранить файл».

Это скорее:

«Я считаю эту версию проекта значимой и хочу оставить её в истории».

Например:

commit 1
↓
commit 2
↓
commit 3
↓
commit 4

И теперь, если мы сделали глупость на этапе 4, у нас есть возможность посмотреть:

«А каким проект был на этапе 3?»

И это уже очень мощная идея.

Так что же такое git?

git — это система контроля версий.

Ключевое слово здесь — версий.

git следит за тем, как изменяется наш проект.

Причём git работает на нашем компьютере.

Это важно.

git — не GitHub.

А тогда что такое GitHub?

Представьте:

git — это ваш личный дневник проекта.

Он лежит у вас на компьютере.

Но однажды вы понимаете:

«А было бы неплохо иметь копию этого проекта где-нибудь в интернете».

И появляется GitHub.

GitHub — это сервис, который позволяет хранить Git-репозитории в интернете и работать с ними вместе с другими людьми.

Поэтому:

git = инструмент контроля версий

а

GitHub = онлайн-платформа для git-репозиториев

Можно сказать ещё проще:

git умеет помнить. GitHub умеет хранить эту память в интернете и делиться ею с другими.

Репозиторий

Теперь появляется ещё одно слово:

repository — репозиторий.

Репозиторий — это проект, который находится под контролем Git.

Например, у нас есть:

LecturesCPP - Это репозиторий.

В нём могут находиться:

[README.md](http://README.md)
	|
lecture-01
	|
lecture-02
	|
lecture-03
	|
	…

Но самое интересное находится внутри скрытой папки:

.git

Именно там git хранит информацию об истории проекта.

Поэтому репозиторий — это не просто папка.

Это:

папка проекта + история его изменений.

А теперь появляется очень важная вещь — ветки

Представьте дерево.

У дерева есть ствол.

Пусть ствол — это:

main

Это основная линия развития проекта.

Но мы можем от ствола пустить ветку.

Например:

main

│
├──── lab-01
│
├──── lab-02
│
└──── lab-03

И вот здесь начинается магия.

Мы можем работать над lab-01, не ломая main.

Можно экспериментировать.

Можно ошибаться.

Можно написать совершенно ужасный код.

Можно всё сломать.

И при этом сказать:

«Спокойно. Это всего лишь моя ветка lab-01. Основной проект я не трогал».

И именно это нам понадобится на лабораторных

Теперь представьте наш учебный курс.

У преподавателя есть репозиторий:

CPP

В нём лежат задания.

Вы получаете своё собственное хранилище:

Lastname-CPP-Labs-2026

И вот здесь возникает интересная ситуация.

У нас теперь есть два GitHub-репозитория.

Один принадлежит преподавателю:

CPP

Второй — студенту:

Lastname-CPP-Labs-2026

Но git должен понимать:

«А какой репозиторий где?»

И здесь появляются два очень важных слова:

origin и upstream.

Origin

origin — это имя, которое git обычно даёт репозиторию, из которого мы клонировали проект.

В нашем учебном сценарии:

origin
   ↓
репозиторий студента

То есть:

origin — мой репозиторий.

Например:

GitHub
└── Lastname-CPP-Labs-2026

Upstream

А репозиторий преподавателя мы назовём:

upstream

Получается:

upstream
   ↓
  CPP

И теперь у студента в голове должна появиться вот такая картина:

             GitHub

    ┌─────────────────────┐
    │                     │
    │  CPP                │
    │  преподаватель      │
    │                     │
    └─────────┬───────────┘
              │
           upstream
              │
              ↓
      ┌───────────────┐
      │   компьютер   │
      │               │
      │ Student       │
      └───────┬───────┘
              │
            origin
              │
              ↓
    ┌────────────────────────┐
    │                        │
    │ Lastname-CPP-Labs-2025 │
    │ студент                │
    │                        │
    └────────────────────────┘

И вот теперь начинается настоящее программирование.

А как студент получает задание?

Преподаватель добавил новое задание в CPP.

Студент говорит:

«Git, покажи мне, что нового появилось у преподавателя».

И выполняет:

	git fetch upstream

fetch означает:

«Посмотри, что нового появилось там, но пока ничего у меня не меняй».

Это очень полезная привычка.

Мы сначала смотрим, что приехало.

А потом решаем, что с этим делать.

А теперь начинается лабораторная

Допустим, лабораторная №1.

Мы не будем писать её непосредственно в main.

Почему?

Потому что main — наша спокойная, основная линия.

Мы создаём отдельную ветку:

lab-01

Команда:

git switch -c lab-01

Теперь мы находимся здесь:

main
│
└──── lab-01 ← мы здесь

И начинаем работать.

Работаем, ошибаемся, исправляем

Пишем программу.

Исправляем.

Компилируем.

Получаем ошибку.

Исправляем.

Снова компилируем.

Получаем другую ошибку.

Исправляем.

И наконец:

«Ура! Работает!»

Теперь очень важно сохранить результат.

Мы говорим git:

	git add .

Это примерно:

«Вот эти изменения я хочу подготовить для сохранения».

А потом:

git commit -m “lab 01”

И это уже:

«Зафиксируй эту версию проекта в истории».

Commit — это наша точка во времени

Получается:

main
│
└── lab-01
    │
    ● commit
    │
    ● commit
    │
    ● commit

Каждая точка — это сохранённая версия.

И если завтра вы скажете:

«Ой… Я вчера всё сломал».

git ответит:

«Не переживай. Я помню, каким всё было вчера».

Но пока это всё находится на компьютере

И вот тут появляется GitHub.

Мы хотим отправить свою работу в свой удалённый репозиторий.

Для этого:

git push

И происходит:

компьютер
		│
	push
	  ↓
	GitHub

Теперь ваша ветка lab-01 находится и у вас на компьютере и на GitHub.

Например:

Lastname-CPP-Labs-2026
  |
main
  |
lab-01

И вот здесь надо запомнить одну вещь

Commit и push — это НЕ одно и то же.

Это очень частая ошибка новичков.

git commit

означает:

«Я сохранил изменения в истории git на своём компьютере».

А:

git push

означает:

«Я отправил свои commits на удалённый репозиторий».

То есть:

изменили файлы

git add

↓
закомитили ( сохранили текущее состояние кода или файлов в истории проекта)

git commit

сохранили на сервере

↓

git push

↓

GitHub

# А что происходит со следующей лабораторной?

Мы не продолжаем писать всё в ветке `lab-01`.

Мы создаём ветку:

`lab-02`

Потом:

`lab-03`

Потом:

`lab-04`

И получается:

```text
main
│
├──── lab-01
│
├──── lab-02
│
├──── lab-03
│
└──── lab-04

Каждая лабораторная — своя ветка.

Это позволяет нам не смешивать разные работы.

А зачем вообще всё это?

Потому что через некоторое время ваши проекты перестают быть маленькими.

Сначала у вас:

main.cpp

Потом:

10 файлов

Потом:

50 файлов

Потом над проектом работает несколько человек.

И возникает вопрос:

«Кто изменил этот файл?»

«Что было до этого?»

«Почему вчера всё работало?»

«Можно вернуть предыдущую версию?»

«А можно я попробую новую идею, не разрушая основной проект?»

И вот тут git превращается из «какой-то программы, которую заставляет использовать преподаватель» в один из главных инструментов разработчика.

И самое красивое — git помнит не только файлы

git помнит историю проекта.

Например:

a82f31 add laboratory 3
91bc52 fix array input
3fa721 add laboratory 2
7d451a initial project

Мы можем посмотреть:

	git log

И увидеть:

Как проект пришёл к тому состоянию, в котором он находится сейчас.

Получается почти дневник программиста.

Только вместо:

«Сегодня я написал функцию и понял, что ничего не понимаю».

там:

add function
fix bug
refactor
add tests
fix input

Хотя первое иногда тоже полезно было бы сохранять. 😄

И ваша жизнь в git будет выглядеть примерно так

Получили задания:

git fetch upstream

Создали ветку:

git switch -c lab-01

Работаете.

Подготовили изменения:

git add .

Зафиксировали:

git commit -m “lab 01”

Отправили на GitHub:

git push -u origin lab-01

А дальше — следующая лабораторная.

lab-01

lab-02

lab-03

lab-04

…

И последнее

Не надо воспринимать git как набор страшных команд.

git — это способ думать об изменениях.

Вы не просто:

«поменяли код».

Вы говорите:

«Я сделал изменение. Оно имеет смысл. Я хочу сохранить его в истории».

Вы не просто:

«залили код на GitHub».

Вы говорите:

«Я отправил свою историю изменений в удалённый репозиторий».

Вы не просто:

«создали новую папку для лабораторной».

Вы говорите:

«Я создал отдельную ветку для независимой работы».

И тогда git перестаёт быть магией.

Финальная фраза

«Программист — это не тот, кто никогда не ошибается.

Программист — это тот, кто умеет ошибаться так, чтобы можно было вернуться назад».

А git как раз даёт нам такую возможность.

Поэтому сегодня вы научились не просто нескольким командам.

Вы получили возможность экспериментировать с кодом, не боясь его потерять.

А это, пожалуй, один из первых признаков взросления программиста.
